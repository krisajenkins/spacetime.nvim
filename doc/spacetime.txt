1. INTRODUCTION                                        *spacetime-introduction*

spacetime.nvim integrates the SpacetimeDB CLI with Neovim.

The plugin is still early: the browsing interface is under construction. The
full command set is defined and completes its arguments, but several commands
are placeholders that say so when you run them — see |spacetime-commands|.
What works today is connection resolution (|:SpacetimeStatus|) and the browser
itself (|:Spacetime|, |:SpacetimeRows|, |:SpacetimeSchema| and
|:SpacetimeLogs|): the window layout, a sidebar listing your databases and the
tables and views inside them, `<CR>` on a table to see its rows — sorted,
paged, yanked or floated in full — the schema of a table alongside the module's
reducers, and a static view of a database's logs. Following the logs live is
the next piece.

==============================================================================
2. REQUIREMENTS                                        *spacetime-requirements*

• Neovim >= 0.11.0
• The `spacetime` command-line tool >= 2.0.0
• curl - used for all HTTP requests to SpacetimeDB

HEALTH CHECK                                                *spacetime-health*
                                                        *:checkhealth-spacetime*

Run |:checkhealth| spacetime to verify your setup: >

    :checkhealth spacetime
<
It reports:

• Your Neovim version (warns if older than the minimum supported).
• Whether the `spacetime` executable is on your PATH, and its version (warns
  if older than the minimum supported).
• Whether `curl` is on your PATH, and its version.
• A "connection" section carrying the same five fields as |:SpacetimeStatus|,
  from the same code, so the two cannot disagree. It never prints your token
  either.

3. INSTALLATION                                        *spacetime-installation*

With lazy.nvim: >lua

    {
      "krisajenkins/spacetime.nvim",
      config = function()
        require("spacetime").setup()
      end,
    }
<

4. CONFIGURATION                                      *spacetime-configuration*

Call |spacetime.setup()| with a table of options. Every field is optional and
unset fields keep their defaults. >lua

    require("spacetime").setup({
      log_level = vim.log.levels.INFO,
      identity = nil,
      side = "left",
      width = 30,
      log_lines = 200,
    })
<
                                                       *spacetime-opt-log_level*
log_level ~
    Type: `number`, default: `vim.log.levels.INFO`

    Minimum severity for the plugin's own |vim.notify()| messages. Set to
    `vim.log.levels.DEBUG` when diagnosing a problem.

                                                        *spacetime-opt-identity*
identity ~
    Type: `string`, default: `nil`

    Overrides the identity derived from your token's claims; a last-resort
    escape hatch. The account identity is normally computed from the token's
    `iss` and `sub` claims, so it should never need setting by hand — but if
    that derivation goes wrong, a 64-character hex identity here (e.g.
    `"c200..."`) skips it entirely.

                                                            *spacetime-opt-side*
side ~
    Type: `string`, default: `"left"`

    Which side of the tabpage the sidebar opens on: `"left"` or `"right"`.
    Anything else is rejected by |spacetime.setup()|.

                                                           *spacetime-opt-width*
width ~
    Type: `number` or `string`, default: `30`

    How wide the sidebar is, either as a number of columns (`30`) or as a
    percentage of the screen written as a string (`"20%"`). A percentage is
    resolved against the terminal's width each time the layout is opened, so
    one setting suits a wide and a narrow terminal alike; the result is never
    allowed below 10 columns, and always leaves at least one column for the
    content window.

    A width of zero or less, or a malformed percentage such as `"20"` or
    `"120%"`, is rejected by |spacetime.setup()|.

    The sidebar window is created with 'winfixwidth', so ordinary window
    commands will not resize it behind your back — and if you resize it by
    hand, re-opening the layout leaves your width alone.

                                                       *spacetime-opt-log_lines*
log_lines ~
    Type: `number`, default: `200`

    How much log backlog |:SpacetimeLogs| asks the server for, as the
    `num_lines` of the request. Zero is allowed and means "no backlog".

    A negative number, or one with a fractional part, is rejected by
    |spacetime.setup()|: the value goes straight into a query string.

5. COMMANDS                                               *spacetime-commands*

The plugin defines ten commands: >

    :Spacetime                  open the browser
    :SpacetimeToggle            open the browser, or close it
    :SpacetimeConnect [nick]    switch server by nickname  (placeholder)
    :SpacetimeDatabases         refetch your database list
    :SpacetimeTables [db]       list a database's tables   (placeholder)
    :SpacetimeRows {tbl}        browse rows of [db.]tbl
    :SpacetimeSchema {tbl}      schema of [db.]tbl
    :SpacetimeLogs[!] [db]      show a database's logs (! placeholder)
    :SpacetimeLogsStop          stop following logs        (placeholder)
    :SpacetimeStatus            print the resolved connection
<
A command marked (placeholder) exists, accepts and completes its argument, and
reports that it is not implemented yet. It never raises an error — the feature
has simply not landed.

COMPLETION                                              *spacetime-completion*

|:SpacetimeConnect| completes the server nicknames in your `cli.toml`.
|:SpacetimeTables| and |:SpacetimeLogs| complete database names;
|:SpacetimeRows| and |:SpacetimeSchema| complete `db.table`, offering both the
source and the SQL spelling where they differ (`spacegym.ledgerEntry` and
`spacegym.ledger_entry`).

                                                    *spacetime-completion-cache*
Database and table completion is served **entirely from what the plugin has
already fetched in this session**. Pressing <Tab> never makes a network
request: completion fires on every keystroke, and traffic you did not ask for
is worse than a short list. The consequence is that a name the plugin has not
seen yet does not complete — run the command once with the name typed out and
it completes from then on.

Nicknames are read from `cli.toml` on each <Tab>. That is a local file read,
not a request, and only the `nickname` of each server block is looked at; the
tokens in that file are never touched by completion.

                                                                   *:Spacetime*
:Spacetime

    Open the SpacetimeDB browser in the current tabpage: a full-height sidebar
    on the side given by |spacetime-opt-side|, at |spacetime-opt-width|
    columns, and a content window beside it. The current window becomes the
    content window; no new tabpage is created. Focus is left on the sidebar,
    where the keys of |spacetime-sidebar| apply.

    The sidebar is then filled with the databases belonging to your identity,
    and the content window shows a placeholder until you select something.

    Idempotent: running it again re-focuses the existing layout rather than
    splitting a second one, and a sidebar you have resized by hand keeps your
    width. If only the sidebar has been closed, only the sidebar comes back.
    The database list is cached for the session, so the second run renders it
    without another request; `r` in the sidebar fetches it again.

    If the enclosing repository's `spacetime.json` (or `spacetime.local.json`)
    names a `database`, that database is expanded for you, so running
    |:Spacetime| inside a module repository lands where you meant.

    Expanding a database fetches its schema; see |spacetime-sidebar|.

    Every failure — an unreachable server, a rejected token, a configuration
    that will not resolve — is written into the sidebar as text. The command
    never raises and never shows you a stack trace.

                                                             *:SpacetimeToggle*
:SpacetimeToggle

    Open the browser if it is closed, close it if it is open. Closing cancels
    any request still in flight, exactly as `q` does.

                                                          *:SpacetimeDatabases*
:SpacetimeDatabases

    Open the browser and fetch the database list again, cache or no cache.
    The sidebar *is* the database list, so this is |:Spacetime| with the
    cached answer thrown away first.

                                                               *:SpacetimeRows*
:SpacetimeRows {[database.]table}

    Open the browser and put that table's rows in the content window, without
    going through the sidebar to find it. Everything under |:Spacetime| then
    applies — the same grid, the same keymaps, the same session cache.

    The database may be left off: |:SpacetimeRows| `member` means the database
    your project's `spacetime.json` names. With no database on either, the
    command says so and does nothing.

    Either spelling of the table is accepted, the source name (`ledgerEntry`)
    or the SQL one (`ledger_entry`), as completion offers both.

    No schema request is made for this. If the database has been expanded in
    the sidebar this session its cached schema supplies the primary-key markers
    and the types a `Ref` resolves through; if it has not, the grid renders
    without them rather than putting a second request on the wire.

                                                             *:SpacetimeSchema*
:SpacetimeSchema {[database.]table}

    Open the browser and describe that table in the content window: its
    columns, its indexes, its constraints, and the whole module's reducers.
    See |spacetime-schema-view| for what each part says.

    The database may be left off and either spelling of the table is accepted,
    exactly as for |:SpacetimeRows|. A view is described too.

    The schema is the one the sidebar caches, so describing a table in a
    database you have already expanded costs no request, and expanding that
    database afterwards costs none either. `r` in the sidebar drops it.

                                                               *:SpacetimeLogs*
:SpacetimeLogs[!] [{database}]

    Open the browser and put that database's logs in the content window: the
    last |spacetime-opt-log_lines| entries, oldest first, as level, timestamp
    and message. >

    spacegym · 11 lines · asked for 200
    Info  2026-08-09T08:43:53.970840Z  Repairing stale view backing tables
    Info  2026-08-09T08:43:53.972374Z  Disconnecting all users
<
    The database may be left off, in which case it is the one the connection
    resolved for the current buffer carries — your project's `spacetime.json`,
    the environment, or |spacetime.setup()|. With no database on either, the
    command says so and does nothing.

    The level is highlighted per severity (`SpacetimeLogError`,
    `SpacetimeLogWarn`, `SpacetimeLogInfo` and the rest), the timestamp is the
    same UTC rendering a Timestamp column gets, and the message is shown
    verbatim. A line that is not a log record is skipped **silently**: one
    malformed line must never cost you the rest of the log.

    Nothing here is cached — a log tail is stale the moment it lands — so
    every |:SpacetimeLogs| makes a request, and running it for a second
    database cancels the first.

    The bang means follow, and follow is not implemented yet:
    |:SpacetimeLogs|! reports that and shows the static log instead, so a bang
    never quietly behaves as though you had not typed it.

                                                            *:SpacetimeConnect*
:SpacetimeConnect [{nickname}]
                                                             *:SpacetimeTables*
:SpacetimeTables [{database}]
                                                           *:SpacetimeLogsStop*
:SpacetimeLogsStop

    Placeholders. Each command exists, takes and completes its argument as
    documented above, and notifies you that it is not implemented yet. Nothing
    they do can fail, because they do not do anything yet.

    |:SpacetimeLogsStop| will stop a log follow once |:SpacetimeLogs|! starts
    one.

                                                            *:SpacetimeStatus*
:SpacetimeStatus

    Print the connection the plugin has resolved for the current buffer, as
    five lines: >

    server:       maincloud (https://maincloud.spacetimedb.com:443)
    identity:     c2005efe02e92547ddd4bd106e84a281ead78a30fa26f42e6...
    token:        present
    cli.toml:     /home/you/.config/spacetime/cli.toml
    project:      /path/to/repo/spacetime.json (database: spacegym)
<
    server ~
        The nickname you asked for, or the hostname if you named one by hand,
        followed by the base URL. The URL carries both the scheme (so `https`
        means TLS) and an explicit port.

    identity ~
        Your 64-character hex identity, derived from the token's `iss` and
        `sub` claims, or taken from |spacetime-opt-identity| if you set it. If
        the derivation fails, the reason is printed on this line rather than
        aborting the command — the remaining lines are still useful.

    token ~
        Always exactly `present` or `absent`. The token itself is never
        printed, not even a prefix of it: this command is meant to be safe to
        paste into a bug report.

    cli.toml ~
        The path to the SpacetimeDB CLI's config, with `(not found)` appended
        when there is no file there. Not having one is fine — environment
        variables and |spacetime.setup()| can supply everything.

    project ~
        The `spacetime.json` / `spacetime.local.json` found at the enclosing
        repository root, and the database they name; `none` when there are
        none.

    If the configuration cannot be resolved at all — an unknown server
    nickname, say — the error appears on the `server` line and the command
    still prints the rest. It never fails outright, because a broken
    configuration is exactly what you would be running it to diagnose.

    The same fields appear under |:checkhealth| spacetime.

6. SIDEBAR                                                 *spacetime-sidebar*

The sidebar lists the databases your identity owns, one per line, each with a
marker: `▸` collapsed, `▾` expanded, `⏸` paused. Its 'filetype' is
`spacetimetree`, so you can hang your own autocommands or mappings off it.

EXPANDING A DATABASE                              *spacetime-sidebar-expanding*

`<CR>` on a database fetches its schema and lists what is inside it: your
tables first, then your views, then SpacetimeDB's own `st_*` system tables.
Each group is in canonical-name order. A table or view is labelled with the
name you wrote it under (`ledgerEntry`), not its SQL name (`ledger_entry`).

The schema is cached per database for the session, so expanding the same
database again is instant and puts nothing on the wire. `r` is the only expiry
the cache has.

While the request is out the node reads `loading…`; collapsing it, or closing
the browser, cancels the request.

                                                     *spacetime-sidebar-paused*
A paused database answers `503` on every endpoint, so it is asked exactly
once. The answer is remembered, the node is marked `⏸`, and expanding it again
asks nothing — pressing `r` on it is how you ask again once it has woken up.
Nothing is ever probed at startup: a pause is only ever discovered from a
request you asked for.

OPENING A TABLE                                       *spacetime-sidebar-rows*

`<CR>` on a table or a view runs >

    SELECT * FROM "table" LIMIT 100
<
and renders the answer in the content window as a grid: a badge line, a header
line, then one line per row. Columns are aligned by display width rather than
by byte count, so `£` (one column, two bytes) and `🎟` (two columns, four bytes)
still line up.

                                                      *spacetime-grid-badge*
The badge on the first line says how many rows are on screen, how far into the
table they start, and how long the server said the query took: >

    100 rows · offset 100 · 1.4ms
<
The duration is the response's own `total_duration_micros`, rendered by the
same code a TimeDuration column goes through. A server that sends none reads
`0s`, which is what we were told.

Primary-key headers, `NULL` cells, identities, connection ids, timestamps and
durations each get their own highlight group. Every group the plugin defines is
a `default` link to a standard group, so your colourscheme wins and `:hi link
SpacetimeNull Comment` is all it takes to change one.

A cell wider than 40 columns is cut and marked with a `…`. Nothing is rounded
or reformatted on the way: a 39-digit identifier is shown to its last digit,
because a browser that quietly loses precision is worse than no browser. The
cut is the grid's, not the data's — `y` and `K` below both give you the whole
value, so nothing on screen is the only copy of anything.

Rows are cached per table for the session, so re-opening a table you have
already looked at puts nothing on the wire; `r` on the sidebar drops that
database's rows along with its schema. Only the first page is cached: the cache
key is the request key, and it carries no offset.

Opening a second table cancels the first table's request, and a response that
arrives after you have moved on is discarded rather than painted over the table
you are now looking at.

A SQL error — an unknown table, a syntax error — arrives from the server as
plain text and is rendered in the content window verbatim: >

    error: Unknown table: widgets
<
SORTING                                               *spacetime-sidebar-sort*

`s` in the content window sorts the grid by the column the cursor is in.
Pressing it again on the same column reverses it; pressing it on another
column starts that one ascending.

The comparison is on the values the server sent, never on the text they are
rendered as. `9` sorts before `10` — a Timestamp column sorts by the instant
and a TimeDuration column by its micros, both of which their formatted text
would get wrong. `NULL` cells, and an Option's `none`, sort last whichever way
round the column is: the direction orders the values, and a missing value is
not one. Equal values keep the order the server sent them in.

Nothing is refetched and no row is rewritten: sorting rebuilds only the
mapping from screen line to row, so the cursor can follow the row it was on
rather than the line it was on, and it stays in the column it was in.

Re-opening a table shows it in the order the server sent it again.

PAGING                                                *spacetime-grid-paging*

`]p` and `[p` turn the page, 100 rows at a time. There is no server-side
cursor, so a page is a `LIMIT`/`OFFSET` window: turning one moves the offset
and asks again. >

    SELECT * FROM "table" LIMIT 100 OFFSET 100
<
Both keys stop rather than beep. `[p` on the first page does nothing, because
the page before it would be a negative offset, and `]p` does nothing on a page
the server returned short, because a page after the last one cannot exist.

Holding `]p` down is safe. Every page of a table is requested under the same
key, so each keystroke cancels the request before it, and a response that lands
after you have paged past it is discarded rather than painted over the page you
are looking at.

A page arrives in the order the server sent it, so `s` sorts the page you are
looking at rather than the table. Only the first page is cached; the others are
fetched each time.

YANKING AND THE ROW DETAIL                              *spacetime-grid-yank*

The grid truncates for the sake of the layout, so three keys exist to give you
what it cut:

    `y`   yanks the cell under the cursor — the whole value, before the grid
        cut it. A String column yanks the string itself, unquoted; a 39-digit
        integer yanks to its last digit.
    `Y`   yanks the whole row as a JSON object, keyed by column name and valued
        by what the server sent rather than by the display text. An integer
        too big for a double is written as a JSON string rather than a number,
        because that is how its digits were preserved.
    `K`   opens a float showing every column of the row, one per line, each
        value untruncated. 'wrap' is on, so a long one is all there. `q` or
        `<Esc>` closes it.

`y` and `Y` put their text in the unnamed register `"`, honouring a register
prefix — `"+Y` puts the row on the system clipboard — and your 'clipboard'
setting exactly as any other yank would. Each reports what it yanked, and how
many bytes, in |:messages|.

KEYMAPS                                              *spacetime-grid-keymaps*

These are buffer-local to the content window while it is showing a grid. >

    s           sort by the column under the cursor (again to reverse)
    ]p          next page
    [p          previous page
    y           yank the cell under the cursor, untruncated
    Y           yank the row as JSON
    K           show the whole row, every column untruncated
<
`y`, `Y` and `K` do nothing but say so when the cursor is on the badge, on the
header or on the `(no rows)` marker: there is no row there to act on.

The content window is shared: |:SpacetimeSchema| paints into the same buffer,
so these keys are taken off it while a schema is showing and put back with the
next table you open. A `]p` left behind could otherwise page a grid that is no
longer on screen.

SCHEMA VIEW                                            *spacetime-schema-view*

|:SpacetimeSchema| describes one table in the content window: >

    ledgerEntry (ledger_entry)
    table · Private · 5 columns · schema v10

    Columns
      entry_id        U64                 PK autoinc
      transaction_id  { __uuid__: U128 }
      security_id     String
      amount          I64
      account         Array<String>

    Indexes
      ledgerEntry_entryId_idx_btree  BTree(entry_id)  accessor entryId

    Constraints
      ledger_entry_entry_id_key  Unique(entry_id)

    Reducers (spacegym)
      ClientCallable  book(instanceId: U64) -> ok {} / err String
      Private         onConnect (on_connect)() -> ok {} / err String
<
The title is the table, the line under it says what kind of thing it is,
whether it is public, how many columns it has and which schema version the
server answered with. Column types are resolved through the module's own
typespace, so a reference reads as the name the module gave it and an
unrecognised newtype is shown as the plain product it is rather than guessed
at. `PK` marks the primary key and `autoinc` a sequence-backed column.

A view has neither indexes nor constraints, and the headings say `(none)`
rather than disappearing.

The reducers are the whole database's, whichever table is on screen. Each is
listed with its parameter names and types and, where the server sends them,
the `ok` and `err` types it returns.

                                                    *spacetime-schema-private*
A reducer is marked `ClientCallable` or `Private` as the server reports it,
and a `Private` one is greyed out rather than hidden: it is part of the
module, it is simply not yours to call.

Servers older than SpacetimeDB 2.0.4 answer with a schema carrying no
visibility field at all. There the marker is omitted entirely rather than
guessed at — an unknown visibility means "assume callable", because labelling
every reducer `Private` would be a claim about your module rather than a
report of what the server said.

                                                      *spacetime-schema-names*
Where a name was written one way in the module and is spelled another way in
SQL, both are shown: `ledgerEntry (ledger_entry)`, `onConnect (on_connect)`.
The SQL endpoint accepts either spelling, so showing the one you wrote is a
convenience rather than a trap. Where the two agree — every v9 schema, and most
v10 names — only the one name is printed.

Nothing in this view is truncated, and it binds no keys of its own.

KEYMAPS                                            *spacetime-sidebar-keymaps*

All of these are buffer-local to the sidebar; nothing is mapped globally. >

    <CR> / o    expand or open the node under the cursor
    r           refresh: drop the cache and fetch again
    q           close the layout
    y           yank the node's name
    gi          yank the database identity
    ?           show this key map
<
Press `?` in the sidebar to print the same list; it comes from the same table
the mappings are built from, so the two cannot disagree.

`y` and `gi` honour a register prefix, so `"+gi` puts the identity on the
system clipboard.

`r` drops the cached database list and fetches it again. On a database node it
also drops that database's own cached schema and rows, and whatever the last
schema request concluded — the cache has no expiry, so this is how you ask for
fresh data. A database still expanded is refilled by the same keystroke.

`q` closes both windows *and* cancels every request still in flight, so a
response cannot arrive after you have closed the browser. The content window
is handed back the buffer it displaced. When the layout is all that is left of
the tabpage, that window stays open with your buffer in it rather than closing
Neovim.

ERRORS                                              *spacetime-sidebar-errors*

Failures render as sidebar text, never as an error message and never as a
stack trace: >

    error: unauthorized: the server rejected the token
<
When only part of the fetch fails — the list arrives but one database's names
do not — the databases that did arrive are still listed, and the one that
failed is expanded to show its own error. Partial data is never thrown away to
report an error, and an error is never swallowed to show partial data.

7. LUA API                                                     *spacetime-api*

                                                            *spacetime.setup()*
require("spacetime").setup({opts})
